# Semantic reasoning contract v0.3 — delivery, evidence and boundaries

**19 October 2026 · editorial/candidate ontology, not approved policy or an SEB production architecture.**

## Product decision

Retain the existing V22 Knowledge Hub and its eight visible orientation concepts. Enhance the *same* `src/semantic/knowledge-to-capability.json` with qualified truth-bearing records, competency questions and adverse reasoning examples. Do not create a disconnected ontology explorer or equate diagram topology with ontology quality.

The browser projection is the `Knowledge & methods` competency workbench, rendered by `src/semantic-atlas.js`, styled in `src/semantic-atlas.css`, using a deterministic **illustrative-only** evaluation function in `src/semantic-reasoning.js`. The same data feeds the build validator and the tests.

## Source and scope integrity

The model extends existing authored Hub example references and a previously generated candidate ontology review. A recent user-provided chat URL was **not readable through available source tools**. The revision makes no claim about the contents of that unread conversation. No internal source passages or actual permission rules were added to this public repository.

## Semantic components

- **8** editorial concepts; **10** qualified illustrative links (not entailing operational links).
- **14** candidate record contracts: SourceVersion, AuthorityBinding, ApplicabilityAssessment, BusinessConcept, SemanticMapping, ContextAssemblyRun, PermissionEvaluation, OutputProposal, AccountableDecision, TestCase, TestResult, KnowledgeChangeProposal, KnowledgePublication and BenefitObservation.
- **7** competency questions, each with required contracts, current honest answer, missing evidence, adverse case and an inspectable authored Hub example.
- **7** generic reasoning fixtures, distinguishing unknown applicability, denied/unknown permission, wrong subject, expired grant, wrong purpose and a fully scoped **example-only** conditional eligibility.
- Distinct vocabularies for applicability, permission, publication review and test-execution state.

## Four prohibitions that must remain executable

1. Unknown applicability is not not-applicable; unknown permission is not an allow. A sample operation is blocked unless applicability, permission, subject, purpose and current grant all satisfy the declared prerequisites.
2. A source reference is not an approved institutional interpretation; a field name or document is not a reviewed semantic mapping or runtime knowledge-consumption trace.
3. A proposed TestCase is not an observed TestResult. An observed result must be pinned to actual run, environment, version and observation; a syntactically complete fake record still needs independent authenticity verification.
4. An output proposal is not a human decision, and feedback or publication does not automatically approve a change.

## Visual system

The 21 local reference boards were inventoried; a contact sheet and three detailed boards informed this iteration. The earlier build had already inspected the supplied deck. The useful reference language is a dark green application header, ivory/sage/stone surfaces, analytical typography, specimen-like objects, concise state labels, selective depth and precise contextual reading. Generated article numbers, current-state claims, owners, metrics and evidence counts were not reused.

The opening is broader than the old requirement/instruction hero. A work-centred composition is followed by a quiet bridge, an inspectable knowledge transformation, representative task paths, and a condition-route illustration. There are three main explanatory graphics, rather than a homepage of equal cards or an abstract layer taxonomy.

Other surfaces use forms suited to their questions: source and observation pair, subject/field structure, instruction diff, impact candidates, evidence scope, object dossier, bounded relationship context and line-indexed source reading. The retained topic reading, scoping forms, search and decision sheet use the same tokens and editorial hierarchy.

`src/explanations.css` defines semantic surface, relationship, review and missing-state tokens. Meaning is conveyed by labels and structure as well as colour. Depth groups artifacts; it does not mean authority or maturity. CSS projections change full desktop relationships into focused tablet columns and ordered mobile reading. Motion is nonessential. These choices have not been rendered in this environment.

SEB Sans Serif is requested locally. Approved portable font binaries were not supplied. The explicit system fallback remains, and no proprietary font is fabricated or impersonated. The reference deck's serif face is not treated as an approved font.

## Architecture

- `explanation-data.js` adds conceptual work-domain descriptors and synthetic transfer objects to the shared registry. It does not duplicate existing objects or change the primary strategy's role.
- `explanations.js` supplies semantic components and reusable explanation patterns, separate from the full reading templates.
- `model.js` supplies deterministic one-/two-hop typed relationship expansion. No graph database, force layout or vector search is implied.
- `views.js` coordinates overview, task, knowledge, condition, source, relationship and evidence projections.
- `app.js` retains the shared controller and history. Search now uses typed results, includes supplied source text, and preserves context when opening object detail.
- `scoping.js` exports both JSON and a review brief from the same effective record. Incompatible local records remain unresolved and recoverable rather than being silently deleted.
- `build.mjs` emits modular and standalone static builds. Relative assets receive a version query to reduce stale-asset mixing after a future authorised deployment.

The relationship view preserves stored direction and wording. Incoming relationships are not silently inverted. Two-hop context does not invent causality. The selected object can be recentered explicitly, or inspected separately. A list representation carries the same edges.
